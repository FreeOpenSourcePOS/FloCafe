# Brief: three blockers from the closing audit

A closing audit of the server code found three ways an order can be charged or printed wrongly. Each is a claim to prove with a failing test before fixing. Read [../README.md](../README.md) and [../contract.md](../contract.md) ("Order lines") first.

1. **A flat discount can shrink by a cent on the next edit** (`main/routes/orders.ts` ~1346). Apply an amount discount of `1.005` to an unpaid order: the route stores a 1.01 discount and keeps 1.005 as the configured value. Add an item or edit a note, and the recompute path rounds that value with `toFixed(2)`, giving 1.00, so the discount shrinks and the amount owed rises. Use the same decimal helper (`discountOn` in `main/services/tax.ts`) for flat discounts on recompute, so the applied amount and every recompute agree. Find every recompute path (append, edit, quantity change, cancel of a line) and test each.
2. **A menu reload can change what the kitchen is told to make for an order already sold** (`shared/pizza/ticket.ts` ~90). A deal's ticket lines end with `INCLUDES: <description>`, read from the menu in force when the ticket prints. Sell a scheduled deal whose description says 12 wings, reload the menu with the same deal id and picks and a description that says 6 wings: at release the ticket prints 6 for an order sold with 12. The description in force at sale has to travel with the order line and be what prints, on every path (kitchen ticket on all renderers, kitchen display, receipts, the cart and the sent-line view of a placed order). Smallest sound way: the server writes the description into the stored recipe when it validates a deal at sale (an optional field the client cannot set and `recipeKey` ignores, so cart-line identity, quick buttons and the "same recipe" comparison in `main/pizza/sold-line.ts` are unaffected), and `ticketLines` prefers it over the menu's. A recipe stored before this change has no such field and prints the menu's description as today. A recipe-only edit of a sent deal keeps the description it was sold with. Say what you chose and prove each of those properties.
3. **The kitchen ticket route can report success without printing** (`main/routes/printers.ts` ~1494). The route prints the saved lines chosen by the ids in the request. If a second terminal replaces the only pending line after the first terminal got the order but before it asked for the ticket, the request names the superseded id, no line matches, and the route answers `success: true` while the replacement still waits. When the requested ids give no printable line and the order still has lines waiting for a ticket, answer a conflict the caller can tell apart (409 with a code), and have the POS refresh the order and ask again once, so the ticket prints. Check the other callers of the route (the Orders page, the Server App, automatic release) do something sensible with that answer.

## Rules

A test first for each (red), then the smallest fix (green). A store with no pizza menu behaves as before, except where the finding is itself an upstream bug (1 and 3): say plainly what changes for such a store. Only the made-up sample menu in tests.
