# Brief: audit fixes, orders, money and printing

An audit by a second reviewer of the server code found the problems below. Each is a claim to prove with a test before fixing. Read [../README.md](../README.md) and [../contract.md](../contract.md) ("Order lines") first, and `tests/pizza-order-recipe.test.ts`, `tests/pizza-tax-bc.test.ts`, `tests/pizza-order-print.test.ts`.

1. **M1, tax a cent short** (`main/routes/orders.ts` ~2489 and the tax adapter it calls). A line amount is price times quantity in binary floating point: three items at 10.70 give 32.099999999999994, which goes to the decimal tax engine, so 5% GST rounds to 1.60 instead of 1.61 and the total is 33.70 instead of 33.71. A stored order subtotal can also read 72.21999999999998. Prove it with a BC-tax store (see `pizza-tax-bc`): 3 x 10.70 with GST 5% must give tax 1.61 and total 33.71. Fix where line amounts are computed for create, append, edit and preview (find every place; they must agree with each other and with the bill): compute in whole cents or with the decimal helper upstream already has (look for it before adding one), and store currency-rounded subtotals. This is upstream code: make the smallest change, list every upstream test whose expected numbers change and why each new number is the right one. If upstream tests pin the old half-cent results, stop and report rather than editing many of them.
2. **M2, a retired item can still be sold** (`orders.ts` ~2444). After a menu load switches a product or variant off, create and append still accept it by id; a retired plain pizza with no variant sent sells at its base price because all its variants are inactive. Find what upstream already enforces for an inactive or deleted product or variant on create and append, then close the gap: a new sale or a quantity increase of an inactive or deleted product or variant is refused with a message a cashier can act on; reductions, voids and refunds of an already-sold line still work. A pizza product with size variants must have a variant.
3. **M3, the ticket can differ from the saved order** (`main/routes/printers.ts` ~1482). The KOT route loads the saved lines but then uses item bodies the client sent, so a stale browser can print a different recipe or drop a removal. Use the requested ids only to select persisted lines of that order; what prints (name, quantity, recipe, note, add-ons) comes from the database. Check how upstream uses the client-sent bodies today (an append prints only new items; a reprint; anything that legitimately is not persisted) and keep that working. The test at `tests/pizza-order-print.test.ts` ~399 expects fabricated item ids to print: rewrite it to put a malformed recipe on a persisted line.
4. **M4, changing a sent pizza re-prices it** (`orders.ts` ~6881). An edit that changes only the recipe (same product, variant, quantity and add-ons) goes through the replacement path and reads current catalogue prices, so after a menu reload the line is charged the new price. When only the recipe (or note) changed, carry the sold line's unit price, add-on prices, discount, override and tax treatment forward. Test: sell, change the menu price by a reload, change one removal: same price; change the size: new price.
5. **M8, omitted recipe and explicit null hash the same** (`orders.ts` ~6092). Reusing an edit's idempotency key with the opposite intent returns the first answer instead of a conflict. Encode absent and null differently in the request hash.
6. **M12, tax-pack receipt templates omit recipe lines** (`main/printers/thermal.ts` ~3312). Classic, compact and merchant receipts print the detail lines; the tax-pack template path prints add-ons and notes only. Use the same detail-line rendering there, including the warning line.

## Rules for every fix

- A test first that shows the problem (red), then the smallest fix (green). If the test shows the problem is not real, keep the test, change nothing, and say so.
- Only the made-up sample menu in tests. A store with no pizza menu and upstream defaults must behave exactly as before unless the finding is itself an upstream bug, in which case say plainly what changes for such a store.
- Do not run the full core suite; CI runs it. Run every `test:pizza-*` script and every script that loads a file you touched, each with a throwaway `HOME`, then `npm run i18n:check`, `npm run test:script-coverage`, `npx tsc --noEmit && npx tsc --noEmit -p frontend/tsconfig.json && npm run lint && npm run lint:budget`, `node scripts/ci/check-changed-format.cjs --base 093bfe64`, `npm run docs:check`.
- Update `pizza/contract.md` and the `docs/` page for anything whose described behaviour changes (present tense, no history).

## Report

Branch and commit; for each id: red then green, or why no change; every upstream file edited with line counts; anything you could not fix as written and why; what you did not verify.
