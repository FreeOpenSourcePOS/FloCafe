# Brief: audit fixes, the browser side

An audit by a second reviewer of the frontend found the problems below. Each is a claim to prove with a test before fixing. Read `docs/architecture/frontend.md` (the pizza sections), [../README.md](../README.md) and [../contract.md](../contract.md) first. Nothing in `main/` changes.

1. **F1, a browser-printed ticket can silently omit a recipe** (`frontend/src/lib/pizza/detail-lines.ts` ~34). When the catalogue is not loaded, or `ticketLines` throws, and the item has no precomputed detail lines, the browser paths print a bare name. The server prints `RECIPE NOT PRINTED - CHECK ORDER` (the `RECIPE_NOT_PRINTED` constant in `shared/pizza/ticket.ts`). An item whose `modifier_selection` is a pizza or deal recipe must get the warning line on every browser path (ESC/POS, raster, HTML ticket, receipt). `tests/pizza-kot-browser.test.ts` Case 2 (~286) asserts the silent behaviour: change it to expect the warning. A plain item or a plain pizza with no recipe still prints nothing extra.
2. **F2, a till keeps an old menu after another device loads a new one** (`frontend/src/lib/pizza/catalog.ts` ~51). The first answer is cached for the session. Smallest sound fix: the catalogue is fetched again when the POS page mounts and when the window regains focus or becomes visible (no more than once every 30 seconds), using a cheap way to tell whether it changed (the stored menu's `imported_at` is on the server; if `GET /api/pizza/catalog` does not return a version, compare the body, and say so), and when it changed the POS product list is refetched too so tiles, prices and the sheet agree. An open sheet or configurator is not swapped under the cashier: the new menu applies when it closes, and if its line no longer fits, saving shows the message the reducer already gives. If the server refuses an order with a stale-menu error (find the messages in `main/pizza/order-recipe.ts`), reload the catalogue then as well.
3. **F3, a tenant switch keeps the previous tenant's menu** (`catalog.ts` ~57). Selecting another tenant changes the token without the login or logout event that clears the cache. Scope the cache and any fetch in flight to the tenant (and user where the app scopes other caches that way; look at how upstream's stores reset on a tenant change) so a tenant with no pizza menu never sees another's screens.
4. **F6, quick buttons survive a session or tenant change** (`frontend/src/components/pos/pizza/useQuickButtons.tsx` ~52). The shared store keeps the previous tenant's buttons, and a failed fetch keeps the old list. Clear buttons, the open dialog and request ownership on the same events as F3; a failed fetch shows no buttons from another scope.
5. **F4, the sheet's price can differ from the charge** (`frontend/src/components/pos/pizza/PizzaSheet.tsx` ~329). The sheet quotes the catalogue's size and dip prices. The cart charges the POS product's variant price (the online price when an online platform is chosen) and keeps a price override on an edited line. Quote from the resolved product, variant and add-ons with the cart's own pricing rule (the same function quick buttons use for `buttonPrice` if it fits), and when editing a line with an override show that the line keeps its own price. The deal configurator's fixed price likewise shows the product's price (`PizzaDeal.tsx` ~96).
6. **F5, drink tiles show the counter price on an online order** (`frontend/src/lib/pizza/small-items.ts` ~109). Use the same pricing rule as F4 for tiles and row labels.

Also fold in two small notes from earlier reviews: in the quick-button save dialog, a preview of a button whose size is sold out says "Sold out" as the page tile does (`QuickButtons.tsx` ~445); and in `frontend/e2e/kot-append-only-print.spec.ts` the settings restore must run even when the cleanup before it fails.

Tests: script tests for the pure parts (catalogue scoping and refresh rule, the price quote, detail-line fallback), chained into `"test"`. One Playwright spec case each for F2 (load an edited menu through the API while the POS is open, bring the page to the front: the tile price changes without signing out) and F4 (an online order with a platform shows the online price in the sheet and the cart agrees), if the e2e fixture has an online price to use; otherwise say why not. Playwright on ports 3431-3433, chromium only, throwaway `HOME`, `PLAYWRIGHT_BROWSERS_PATH=/Users/anmolnoor/.cache/pizza-pos/ms-playwright`, paths as filters; finish with one run of every `e2e/pizza-*.spec.ts` plus pos-actions-menu, pos-keyboard-shortcuts and server-app-ordering.

## Rules for every fix

- A test first that shows the problem (red), then the smallest fix (green). If the test shows the problem is not real, keep the test, change nothing, and say so.
- Only the made-up sample menu in tests. A store with no pizza menu and upstream defaults must behave exactly as before unless the finding is itself an upstream bug, in which case say plainly what changes for such a store.
- Do not run the full core suite; CI runs it. Run every `test:pizza-*` script and every script that loads a file you touched, each with a throwaway `HOME`, then `npm run i18n:check`, `npm run test:script-coverage`, `npx tsc --noEmit && npx tsc --noEmit -p frontend/tsconfig.json && npm run lint && npm run lint:budget`, `node scripts/ci/check-changed-format.cjs --base 093bfe64`, `npm run docs:check`.
- Update `pizza/contract.md` and the `docs/` page for anything whose described behaviour changes (present tense, no history).
