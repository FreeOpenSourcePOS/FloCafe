# Brief: audit fixes, menu import, recipes, quick buttons and the headless kit

An audit by a second reviewer of the server code found the problems below. Each is a claim to prove with a test before fixing. Read [../README.md](../README.md), [../contract.md](../contract.md) and [../headless.md](../headless.md) first. Another coder is changing `main/routes/orders.ts`, `main/routes/printers.ts` and `main/printers/thermal.ts` at the same time: do not edit those.

1. **D5, derived ids collide across sides** (`main/pizza/menu-import.ts` ~172). Ids are joined with hyphens, so side `a` with modifier `b-c` and side `a-b` with modifier `c` both map to `ag-a-b-c`; across two loads the old link survives and one side ends up requiring the other's choices. The same join exists for other derived ids (pizza `a-b` with size `c` against pizza `a` with size `b-c`, drink and variant, add-on ids). Smallest correct fix: the parser (`shared/pizza/menu.ts`) refuses a menu in which two different entries derive the same id, naming both; and the importer refuses to reuse an existing derived row whose parent differs from the one in the file. Do not change the id scheme (stores and quick buttons hold these ids). Tests for each id kind.
2. **D7, a deal no order could fit** (`shared/pizza/menu.ts` ~190). A deal asking for 500 pizzas passes the menu check, but its recipe exceeds the 20 KB cap. Cap the pizzas in one deal (pick a bound the recipe format fits with every pizza a half and half with the most removals the caps allow; say how you derived it) and the cans in a pop pick.
3. **D11, the 20 KB cap counts UTF-16 units** (`shared/pizza/recipe.ts` ~32). Measure the UTF-8 byte length of the serialized recipe. `shared/` cannot import Node built-ins; use what the lint rules allow (`TextEncoder` is available in both runtimes; check the rule).
4. **D9, the restricted kitchen projection passes a whole stored selection** (`main/pizza/order-recipe.ts` ~132). Whenever `kind` says pizza or deal, the full stored object goes to a restricted station, so a legacy or malformed selection can carry extra fields. Project only the versioned recipe fields; return null when the selection fails the structural check.
5. **D10, a quick button note longer than an order allows** (`main/pizza/quick-buttons.ts` ~203). A 101 to 140 character note saves and the button is marked usable, but the order route's note limit is 100 by default (find the real rule and whether it is a setting), so a tap builds an order the server refuses. Validate the note with the order route's own rule on save and when working out `usable`. The test at `tests/pizza-quick-buttons.test.ts` ~479 pins acceptance of 140: fix it.
6. **D13, a category whose switch-off was deferred is forgotten** (`menu-import.ts` ~350). When a removed menu category stays on because it still holds a hand-made product, it drops out of what later loads will switch off, so once the product is gone the empty category stays for ever. Keep it eligible. (On this branch the switch-off list is derived from the previous load's stored catalogue; make sure a deferred category survives that rule.)
7. **D6, two restores at once** (`scripts/pizza/headless/restore.cjs` ~84). The maintenance lock is process-local, so two restore commands can both pass the stopped-service checks and one can remove the database or its sidecar files while the other restores. Take an exclusive lock per data directory (a lock file opened with the exclusive flag, removed on exit, with a stale-lock rule) before checking service state and hold it until the database is closed; `backup.cjs` takes the same lock. Test two concurrent restores: exactly one runs.
8. **D14, health passes with no backup ever taken** (`scripts/pizza/headless/health.cjs` ~18). An absent backup folder always passes. The install takes a first backup once the database is ready, and health requires a recent backup (a threshold tied to the backup timer's period; a store younger than one period passes). Do not install or start systemd units on this machine; test as the existing `tests/pizza-headless-*.test.ts` do.

## Rules for every fix

- A test first that shows the problem (red), then the smallest fix (green). If the test shows the problem is not real, keep the test, change nothing, and say so.
- Only the made-up sample menu in tests. A store with no pizza menu and upstream defaults must behave exactly as before unless the finding is itself an upstream bug, in which case say plainly what changes for such a store.
- Do not run the full core suite; CI runs it. Run every `test:pizza-*` script and every script that loads a file you touched, each with a throwaway `HOME`, then `npm run i18n:check`, `npm run test:script-coverage`, `npx tsc --noEmit && npx tsc --noEmit -p frontend/tsconfig.json && npm run lint && npm run lint:budget`, `node scripts/ci/check-changed-format.cjs --base 093bfe64`, `npm run docs:check`.
- Update `pizza/contract.md` and the `docs/` page for anything whose described behaviour changes (present tense, no history).
