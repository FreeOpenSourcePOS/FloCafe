# Brief: the price guard and the POS retry paths

The price guard (see [price-guard.md](price-guard.md)): the POS sends `expected_subtotal`, the pre-tax amount it showed, and the create and add-items routes refuse with 409 `PRICES_CHANGED` when their own figure differs. A review found it does not fit how the POS retries a request whose answer was lost. Read the POS page's order paths and its stored-attempt and idempotency handling (`frontend/src/app/(dashboard)/pos/page.tsx`, and whatever it uses to store an append attempt and to build an idempotency key or fingerprint), `frontend/src/lib/pizza/price-guard.ts`, `frontend/src/components/pos/pizza/usePriceGuard.tsx`, `main/pizza/price-guard.ts` and `tests/pizza-price-guard.test.ts` before changing anything.

- **G1 (blocker) `pos/page.tsx` ~1555: append recovery drops `expected_subtotal`.** If the first add-items request never reaches the server and prices change before the till reloads, recovery re-sends the stored attempt without the field and the items go on at the new price. Store the quoted subtotal with the append attempt, replay it with the same key, and on `PRICES_CHANGED` clear the attempt and give the lines back to the cashier for review (in the cart, re-priced, with the message).
- **G2 (blocker) `pos/page.tsx` ~2314: a new quote can turn a retry into a second order.** If a postpaid create commits but its answer is lost, and the cart is then re-priced after a price change, the request fingerprint changes and a new idempotency key is allocated: a second order. Prepaid and send-to-payment retries can instead reuse a key with a changed body and get an idempotency conflict. Keep the original quoted request with its key until that attempt is resolved (committed or refused), and resolve it before any new quote is submitted. `expected_subtotal` must not be part of what makes two requests "different orders".
- **G3 (blocker) `frontend/src/lib/pizza/price-guard.ts` ~25: the guard can authorize a different subtotal from the one the cashier saw.** For a weighed item the cart displays 1.69 while the request sends 1.70 and the server accepts it; and an append to an existing online order is priced with that order's platform prices while the cart displays standard prices. The amount on screen and the amount sent must be one calculation in one pricing context: make the cart's displayed subtotal use the same decimal-correct line calculation the guard sends (the existing `draftLinesTotal` or better), and when the cart is adding to an existing order show the prices of that order's context. The test that pins "1.69 shown, 1.70 sent" (`tests/pizza-price-guard.test.ts` ~351) changes to "1.70 shown and sent". This touches upstream's cart total: change the smallest thing, and list every upstream test whose expected numbers change.
- **G4 (should) `usePriceGuard.tsx` ~21: a published menu refresh leaves existing cart lines stale until a price conflict.** If the new menu removed toppings, submitting fails add-on validation before the subtotal check, so the refresh and the off-sale mark never run and the cashier sees only a refusal. Re-price and mark the cart's lines whenever refreshed lists are published (the combined swap in `frontend/src/lib/pizza/catalog.ts`), and also refresh on a stale-selection refusal from the server (find the messages or codes the order routes use for an add-on or product that is no longer on sale).
- Also document, in `pizza/contract.md` where the guard is described: equal and opposite price changes pass the guard because the total is unchanged (the guard compares totals, not lines).

Tests: script cases for each of G1 to G4 on the pure parts (the stored attempt's contents, the fingerprint, the displayed and sent subtotal for every line shape in the existing test, the re-price on publish); Playwright cases in `frontend/e2e/pizza-price-guard.spec.ts` for G1 (drop the first add-items request at the network, change a price, reload, recovery is refused and the lines come back) and G2 (commit the create but drop its answer, change a price, place again: exactly one order exists). Playwright on ports 3421–3423.
